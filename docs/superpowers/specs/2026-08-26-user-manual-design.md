# NanoVNA-D fork user manual — design

Status: Approved 2026-08-26 (design agreed in conversation; this file records it).

## Purpose

A complete, source-derived user manual for this firmware (1.2.53-sg and later), replacing
the 2019-era nanovna.com pages (mirrored in `research/nanovna-manual/`, ~2,300 operating
words, nothing on MEASURE, SD, console, marker search, band settings, or fork features).

Audience: users of this fork, written as *the* manual for the firmware — DiSlord's features
and the fork's additions treated as one product, with a single appendix listing which
sections describe fork-only features so stock-firmware readers know what they will not see.

Outputs: Markdown chapters (readable on GitHub), one self-contained HTML, one PDF. All from
one source. Publishable at any time; captures can be added incrementally.

## Structure

`docs/manual/` — numbered Markdown chapters, one file each:

| File | Chapter | Source of truth |
|---|---|---|

| `02-sweep-and-traces.md` | Stimulus (start/stop/center/span/CW/points/bandwidth), channels, the 31 trace formats with one line each, scale/ref, e-delay, S21 offset | `trace_info_list` (generated table), `ui.c` |
| `03-calibration.md` | Error model as implemented (Ed/Er/Es, Ex/Et, enhanced response), what each standard contributes, LOAD R, interpolation on range change, slots, what invalidates a cal, THRU re-cal note | `main.c` cal code |

Generated chapters begin with a header: `<!-- generated by tools/manual/<script> — do not edit -->`.

## Generators (`tools/manual/`)

All Python 3, standard library only, run from the repo root.

- `layout.py` — parses `nanovna.h` for both targets' layout constants (LCD size, OFFSETX/Y,
  WIDTH/HEIGHT, NGRIDY, CELLOFFSETX, font sizes, menu button geometry, palette RGB565 values).
  Single place all renderers import from.
- `fonts.py` — parses `fonts/Font5x7.c`, `fonts/Font6x10.c`, `fonts/Font11x14.c`,
  `fonts/numfont16x22.c` bitmaps; renders text to SVG rects (or a compact path per glyph) at
  1:1 pixel scale. Mockups therefore use the firmware's actual glyphs.
- `gen_menus.py` — parses every `const menuitem_t menu_*[]` in `ui.c` (labels including
  `\n`, `R_LINK_COLOR "%…"` value placeholders, `MT_SUBMENU` targets, `#ifdef` guards) into a
  tree rooted at `menu_top`. Emits `09-menu-map.md` (indented tree with per-item description
  hooks) and `docs/manual/img/menu-<name>-<H|H4>.svg` for each menu, drawn with the real
  button height rule (`MENU_BUTTON_HEIGHT(n)`), colours, and font. Items behind guards not
  active for a target are omitted for that target and listed in the appendix.
- `gen_console.py` — parses the command table and each `usage:` string in `main.c`; emits
  `08-console.md`. Descriptions come from a checked-in `tools/manual/console_desc.json`
  (hand-written, keyed by command) so a new command without a description shows as
  `[describe]` in `make status`.
- `gen_formats.py` — parses `trace_info_list` in `plot.c`; emits the trace-format table
  (name, unit, default scale, S11/S21 availability) included by `02-sweep-and-traces.md`.
- `gen_screens.py` — renders plot-screen mockups from scene files
  `tools/manual/scenes/<id>.json`: target, stimulus, traces (format, channel, scale, ref),
  marker positions, optional measure-panel lines, optional synthetic data model (series-RLC
  antenna, thru, open). Output `docs/manual/img/<id>-<H|H4>.svg`. Every mockup carries a
  caption "simulated" in the manual.

Parsers are deliberately narrow (regex over the known table shapes); they fail loudly on
anything unrecognised rather than silently dropping items, and `tests/test_manual_gen.py`
asserts the parsed counts against known values (after preprocessing per target: 44 menu
table definitions / 324 raw items on F303, 43 / 310 on F072; 62 console commands; 31 trace
formats) so a source change that breaks parsing is caught.

## Captures (`tools/manual/capture.py`)

Checklist runner over the USB serial console using the firmware's `capture` command
(RLE8 framebuffer dump, decoded to PNG). `tools/manual/captures.json` lists entries:
`id`, `prompt` (what to connect / do), `setup` (console commands sent first: sweep range,
trace formats, marker, menu state where reachable), `target`. Output
`docs/manual/captures/<id>.png`. Skips existing files unless `--redo <id>|all`.
`--list` shows done/pending. Serial port autodetected (`/dev/ttyACM*`), overridable.

Planned first session (H4): calibration screens (before/after, cal status letters), a
calibrated thru (S21 logmag+phase), open/short/load on Smith, an antenna SWR sweep with
SWR ANT alongside, SWR BW panel on that dip, RESONANCE panel, the about screen, SD browser.

## Build (`docs/manual/Makefile`)

- `make` — run generators, then pandoc → `dist/NanoVNA-manual.html` (self-contained, images
  inlined as data URIs) and pandoc + XeLaTeX → `dist/NanoVNA-manual.pdf` (SVG figures
  converted with `rsvg-convert` to PDF). Title page carries firmware version (from `main.c`
  VERSION) and git describe.
- `make status` — lists pending captures (entries in `captures.json` without a file),
  `[verify on hardware]` markers, `[describe]` console entries, and menu items without a
  description hook.
- Missing capture → the build substitutes the mockup named by the entry's `fallback` scene
  (every capture entry has one) with caption "simulated; capture pending". The build never
  fails for a missing capture.
- `dist/` is committed and attached to GitHub releases so the manual is versioned with the
  firmware. Tools required: pandoc, xelatex (texlive), rsvg-convert — all present on the
  build machine; documented in `tools/manual/README.md`.

## Truthfulness rules

- Every number or behaviour claim is either read from the code (footnote with `file:line`
  or function name) or measured on hardware by the user (stated as such, with the date).
- No "typically" / "usually" claims without a source.
- Every screen is labelled either "captured" (real) or "simulated" (mockup).
- Anything not establishable from the code gets a literal `[verify on hardware]` marker in
  the text, which `make status` lists; markers are resolved by a capture or a bench note.
- Fork-only features are indexed in appendix A; the body does not otherwise mark them.

## Repository notes

- `.gitignore` currently ignores `*.py`, `python`, and `*png` (upstream habits). The manual
  tooling needs negations: `!tools/manual/**/*.py`, `!tests/*.py`,
  `!docs/manual/captures/*.png`, `!docs/manual/img/*.png`. Add these in step 1 and verify
  with `git check-ignore`.
- `research/` (mirrored nanovna.com pages, third-party content) stays ignored and is never
  quoted at length; the manual is written fresh from the source.
- Third-party fonts: none. Mockups use the firmware's own bitmap fonts (GPL, same as the code).

## Out of scope

- RF and antenna theory beyond what a menu needs to make sense.
- PC applications (NanoVNA-Saver, NanoVNA-App) beyond the console protocol they use.
- Other hardware families (V2 / SAA-2 / LiteVNA) — different firmware.
- Translations.

## Order of work

1. `layout.py`, `fonts.py`, `gen_menus.py` → menu map chapter and all menu mockups; parser
   test. Useful on its own and proves the renderer.
2. `03-calibration.md` and `01-orientation.md` (the two chapters with the most new content).
3. `capture.py` + `captures.json`; first capture session on the H4.
4. `gen_console.py`, `gen_formats.py`, `gen_screens.py`; remaining chapters.
5. Makefile, HTML/PDF polish, `make status`, attach `dist/` to the next release.

Each step is a separate plan task with its own review; the manual is publishable after any
step from 2 onward.
